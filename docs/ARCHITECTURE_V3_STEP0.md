# Fitnote v3 — архитектура, шаг 0: фундамент

Ответ архитектора на раздел 3 брифа [fitnote_v3_0.md](fitnote_v3_0.md) с учётом всех приложений (см. [README_SPEC_INDEX.md](README_SPEC_INDEX.md)) и запроса на QR-шеринг.

Шаг 0 почти не меняет то, что видит пользователь. Он закладывает основы, без которых каждую функцию v3 пришлось бы переделывать: мастер старта, конструктор, «Вариацию», «Спасти неделю», профили, три языка и шеринг.

## 0. Неизменные ограничения

1. **Офлайн.** Всё, что нужно на площадке, работает без сети. Сеть нужна только для первой загрузки приложения и обновлений.
2. **Без бэкенда.** Данные живут на устройстве, обмен идёт через файлы, ссылки и QR.
3. **Обратная совместимость.** Существующий журнал, максимумы, планы и незавершённая тренировка переносятся без потерь. Импорт JSON от тренера или ИИ в старом формате (`{workouts, exercises}`) продолжает работать.
4. **Приложение рабочее после каждого шага.** Каждый шаг выкатывается отдельной версией.

## 1. Текущее состояние (что мешает v3)

| Проблема | Где | Чем мешает |
|---|---|---|
| Весь каталог (названия, подсказки, `checkup_max`) копируется в `localStorage` | `utils/storage.ts`, `FitnoteData.exercises` | Новую версию каталога не доставить; не перевести на три языка; максимумы общие, а не у каждого человека свои |
| Тренировка — список конкретных упражнений с числом | `WorkoutPlan.items` | Невозможно адаптировать под другого человека, экипировку или `NO TOUCH`: нет смысла слота (паттерн, ступень, интенсивность) |
| Одна плоская структура без версии схемы | ключ `fitnote_offline_store_v1` | Профили и новые модели некуда положить; нет механизма миграций |
| Нет резервной копии | — | Потеря журнала при очистке браузера или смене телефона |
| Логика внутри компонентов | `WorkoutPlayer.tsx` (около 1 900 строк), `App.tsx` | Генератор, лестницу и калибровку негде переиспользовать и нечем тестировать |
| Нет адресов экранов | вкладки через `useState` | Ссылке шеринга и мастеру старта некуда вести |
| Строки интерфейса зашиты в разметку | все компоненты | Три языка потребуют перебрать каждую строку |

## 2. Решение 1: каталог отдельно от данных пользователя

### Принцип
- **Каталог** — данные в коде, версия приложения = версия каталога. Упражнение идентифицируется постоянным `id` (нынешние id сохраняются: `strict-pull-ups`, `side-plank`…).
- **Пользователь** хранит только своё: максимумы по `id`, свои упражнения, шаблоны, журнал.
- Тексты каталога (название, подсказка, описание техники) лежат в словарях по `id`, а не в объекте упражнения. Так каталог переводится без изменения структуры.

### Модель

```ts
// src/domain/catalog/types.ts
export type MovementPattern =
  | 'push_h' | 'pull_h' | 'push_v' | 'pull_v'
  | 'squat' | 'hinge' | 'lunge' | 'core';
export type EquipmentTag = 'bodyweight' | 'pullup_bars' | 'suspension' | 'bands' | 'weights';
export type EnvironmentTag = 'outdoor' | 'home';
export type PostureTag = 'standing' | 'hands_only' | 'floor_contact';
export type StabilityType = 'bilateral' | 'unilateral' | 'unstable';
export type DifficultyRank = 1 | 2 | 3 | 4 | 5; // -- / - / Base / + / ++

export interface CatalogExercise {
  id: string;                    // постоянный, никогда не переиспользуется
  pattern: MovementPattern;
  rank: DifficultyRank;
  metric: 'reps' | 'seconds';
  isPaired?: boolean;
  environments: EnvironmentTag[];
  equipment: EquipmentTag[];     // любой из списка достаточен
  posture: PostureTag[];
  stability: StabilityType;
  family: string;                // семейство лестницы, может объединять паттерны (раздел 12)
  ladder?: { minus1?: string; plus1?: string }; // предпочтительные соседи
  targetMuscles: string[];
  antagonistMuscles: string[];
  svgKey: SvgKey;
  defaultMax: Record<FitnessLevel, number>; // стартовые максимумы без чек-апа
  teenAllowed?: boolean;         // false для ++ с высокой осевой нагрузкой
}
```

- **Лестница вычисляется, а не хранится ссылками.** Соседи по лестнице — упражнения того же `pattern` с рангом ±1/±2, отфильтрованные по среде и экипировке. Явные ссылки `ladder.minus1/plus1` из ТЗ допустимы как необязательная «предпочтительная» связь, но не обязательны. Так своё упражнение пользователя встраивается в лестницу автоматически: достаточно указать паттерн и ранг.
- Свои упражнения пользователя (`isCustom`) имеют ту же форму плюс поля `name`, `cue`, `videoUrl` прямо в объекте (язык один, с фолбэком отображения).

### Разметка текущих упражнений

Источник истины — `src/data/catalog.ts` (сделано в шаге 0.4). Проверка разметки — `src/domain/catalog/catalog.test.ts`.

## 3. Решение 2: тренировка из слотов

Ключевое решение для шеринга, «Вариации», «Спасти неделю», замены `⇄` и генератора.

```ts
// src/domain/plan/types.ts
export type TargetSpec =
  | { kind: 'fixed'; value: number }          // ровно столько (планы тренера, старые данные)
  | { kind: 'pctMax'; pct: number }           // доля от максимума: 0.3 = AGT, 0.75 = сила
  | { kind: 'rir'; rir: 0 | 1 | 2 | 3 };      // «до запаса N» — оценка по максимуму

export interface Slot {
  pattern: MovementPattern;
  rank: DifficultyRank;          // желаемая ступень
  exerciseId?: string;           // закреплённое упражнение; пусто = подобрать
  target: TargetSpec;
  stabilityQuota?: 'unilateral' | 'unstable'; // для квоты баланса
}

export interface WorkoutTemplate {
  id: string;
  title: string;
  subtitle?: string;
  goal?: Goal;                   // mobility | maintain | agt30 | strength80
  rounds: number;
  restBetweenExercises: number;
  restBetweenRounds: number;
  mode?: 'steps' | 'roundFlow';
  slots: Slot[];
  original?: { rounds: number; slots: Slot[] }; // «План тренера» (из v2)
  source?: 'seed' | 'coach' | 'generated' | 'shared' | 'user';
}

export interface Program {        // цикл: неделя A/B/C или месяц
  id: string;
  title: string;
  workoutsPerWeek: 1 | 2 | 3 | 4;
  templates: WorkoutTemplate[];
}
```

**Разрешение слота в упражнение** — чистая функция движка:

```ts
resolveWorkout(template, context) => ResolvedWorkout
// context = { catalog, customExercises, maxes, environment, equipment,
//             cleanFloor, ageGroup, locale }
```

1. Если `exerciseId` задан и доступен в текущих условиях — берём его.
2. Иначе (или если закреплённое недоступно, например брусья дома) — ближайшее по рангу упражнение того же паттерна, прошедшее фильтр среды, экипировки, `cleanFloor` и возрастных ограничений.
3. Цель: `fixed` → как есть; `pctMax` → `max(min, round(max × pct))`, где `max` — максимум пользователя или `defaultMax` по уровню; секунды округляются до 5.
4. При замене на соседа цель пересчитывается пропорционально максимумам (формула из ТЗ).

Старые планы мигрируют в слоты с `exerciseId` и `target: fixed` — ведут себя ровно как сейчас. Сгенерированные и присланные по QR используют `pctMax` и пустой `exerciseId` — и адаптируются под получателя.

## 4. Решение 3: хранилище v2 с миграцией и резервной копией

### Структура

```ts
// ключ localStorage: 'fitnote_store_v2'
interface StoreV2 {
  schemaVersion: 2;
  activeProfileId: string;
  settings: { locale: Locale; theme: ThemeMode; isMuted: boolean };
  profiles: Record<string, ProfileData>;
}

interface ProfileData {
  profile: UserProfile;          // имя, возрастная группа, уровень, акценты, экипировка, цель, время
  maxes: Record<string, { value: number; date?: string }>;
  customExercises: CustomExercise[];
  programs: Program[];
  activeProgramId?: string;
  selectedTemplateId?: string;
  readiness: ReadinessLevel;
  warmupMinutes: number;
  workoutLogs: WorkoutLog[];     // формат v2 без изменений
  cardioLogs: CardioLog[];
  checkUpHistory: CheckUpEntry[];
  activeSession: ActiveSession | null;
}
```

Журнал (`WorkoutLog`, `SetLog`) не меняется — в нём уже хранится снимок названия упражнения. Добавляются только необязательные поля (например, `pattern` в `SetLog` для аналитики по паттернам).

### Миграция v1 → v2 (один раз при запуске)

1. Нет `fitnote_store_v2`, есть `fitnote_offline_store_v1` → мигрируем.
2. Создаём профиль по умолчанию (имя пустое, мастер старта предложит заполнить).
3. `exercises`:
   - id из каталога → `maxes[id] = { value: checkup_max, date: lastCheckupDate }`;
   - неизвестный id или `isCustom` → `customExercises` (паттерн и ранг — «не размечено», предложить разметить);
4. `workouts` → один `Program` «Мои планы», каждый план → `WorkoutTemplate` со слотами `exerciseId` + `fixed`. Паттерн и ранг слота берутся из каталога.
5. Журналы, кардио, чек-апы, незавершённая сессия, настройки — переносятся как есть.
6. Ключ v1 **не удаляется** в течение одной версии — страховка для отката. Удаляется миграцией следующей версии.
7. Миграции оформлены как цепочка `migrations[n](data) => data(n+1)` — следующие изменения схемы добавляются тем же способом.

### Резервная копия

- «Сохранить копию» → файл `fitnote-backup-YYYY-MM-DD.json` со всем `StoreV2` (или одним профилем).
- «Восстановить» → проверка `schemaVersion`, прогон миграций, предпросмотр (что будет заменено), подтверждение.
- Напоминание о копии раз в N тренировок (настраиваемо).

### Объём
`localStorage` ограничен примерно 5 МБ на сайт. Тренировка в журнале — около 2–4 КБ, то есть порядка 1 000–2 000 тренировок на всё устройство. На годы для нескольких профилей хватает. Если упрёмся — переезд на IndexedDB за тем же интерфейсом репозитория.

## 5. Решение 4: движок отдельно от экранов

```
src/
  domain/            чистые типы и правила, без React и без localStorage
    catalog/         типы, фильтры (среда, экипировка, cleanFloor, возраст), лестница
    plan/            слоты, разрешение, пересчёт целей, AGT, антагонисты
    session/         переходы фаз плеера, перенос между кругами, калибровка
    generator/       генератор тренировки и недели, «Вариация», «Спасти неделю»
    profile/         возрастные группы, рекомендации акцентов мастера
    share/           упаковка и распаковка payload
    rng.ts           детерминированный генератор случайных чисел (seed)
  data/              каталог, тексты каталога, разминка/заминка
  storage/           репозиторий StoreV2, миграции, резервная копия
  i18n/              словари и t()
  ui/                компоненты и экраны
```

Правила:
- `domain/` не импортирует React, `window` и `localStorage`.
- **Генератор детерминированный**: одинаковые входные данные и `seed` дают одинаковую тренировку. Это нужно для шеринга (получатель воспроизводит то же), для «Вариации» (`seed + 1` = следующий вариант) и для тестов.
- Переходы плеера (`completeSet`, `+1 круг`, конец отдыха, перенос значений) — чистые функции `(session, event) => session`. Плеер только отображает и вызывает их.
- Тесты: **Vitest** на все модули `domain/` и на миграции. Перед шагом 0 фиксируем тестами текущее поведение (`calcAgt30`, `getWarmupPlan`, `findAntagonistMatches`, перенос между кругами), чтобы рефакторинг ничего не сломал.

## 6. Решение 5: шеринг, ссылки и QR

### Сценарий
1. Отправитель на экране тренировки или цикла нажимает «Поделиться» → QR и ссылка (можно отправить в мессенджер или соцсеть).
2. Получатель сканирует QR обычной камерой → открывается `https://<домен>/#/s/<payload>`.
3. Если профиля нет — запускается мастер старта (вопросы о себе, цели, экипировке), иначе — короткое подтверждение условий.
4. `resolveWorkout` адаптирует присланные слоты под получателя → предпросмотр → «Сохранить себе».

### Формат payload

```ts
interface SharePayloadV1 {
  v: 1;
  k: 'w' | 'p';                  // тренировка или цикл
  t: string;                     // название
  g?: Goal; r: number; re: number; rr: number; m?: 0 | 1; // цель, круги, отдых, roundFlow
  s: [pattern: number, rank: number, exerciseIdx: number | -1, target: string][];
  // target: 'p30' = 30% максимума, 'f12' = фикс 12, 'r2' = RIR 2
}
```

- Упражнения кодируются **индексом в каталоге**, паттерны — числом: версия каталога только дописывается, индексы не меняются. Неизвестный индекс (у получателя старая версия) — слот подбирается по паттерну и рангу.
- Упаковка: JSON → `CompressionStream('deflate-raw')` → base64url. Поддержка: Chrome 80+, Safari 16.4+, Firefox 113+; если недоступно — без сжатия (одна тренировка помещается и так).
- Бюджет: **до ~800 символов ссылки** — QR версии около 15–20, уверенно читается камерой с экрана телефона. Цикл из 3 тренировок по 6 слотов укладывается с запасом.
- Payload в части адреса после `#` — не уходит на сервер, Cloudflare не видит содержимое.
- QR рисуется локально небольшой библиотекой (выбор на шаге 3: `qrcode-generator` или аналог около 20 КБ), работает офлайн.

### Приватность
В payload — только структура тренировки. **Никаких** имени, возраста, журнала, максимумов отправителя (цели передаются в процентах, а не в его повторениях). Опционально — подпись автора, которую отправитель вводит сам.

### Ограничение, о котором надо сказать пользователям
Получатель, ни разу не открывавший приложение, без интернета его не загрузит. На площадке: отсканировал → открыл по мобильному интернету или дома → установил на главный экран → дальше всё офлайн.

### Маршруты
Минимальный роутер по хэшу, без библиотеки: `#/workout`, `#/checkup`, `#/catalog`, `#/log`, `#/onboarding`, `#/studio`, `#/s/<payload>`. Работает на Cloudflare Pages и в установленной PWA без настройки сервера; кнопка «Назад» на Android ведёт себя ожидаемо.

## 7. Решение 6: локализация

- `src/i18n/ru.ts` — источник ключей; `en.ts`, `tr.ts` типизированы как `typeof ru` — пропущенный ключ ловит компилятор.
- `t(key, params?)` через лёгкий контекст React; язык — `settings.locale` (позже — в профиле), по умолчанию из `navigator.language`, фолбэк `en`.
- Тексты каталога: `catalogText[locale][exerciseId] = { name, cue, details }`, цепочка фолбэка `locale → en → ru`.
- Все **новые** экраны пишутся сразу через `t()`. Существующие экраны переводятся на шаге 4, не блокируя остальное.
- Бриф для ИИ собирается на языке пользователя, ключи JSON-схемы не переводятся.

Это готовит место для интерактивного «15+», калибровки «Как зашёл первый круг?» и слайд-шоу разминки.

## 9. План шага 0 по частям

Каждая часть — отдельный коммит или серия, приложение рабочее после каждой.

| Часть | Что | Видно пользователю | Готово, когда |
|---|---|---|---|
| 0.1 | Vitest, вынос чистых функций в `domain/`, тесты текущего поведения | Нет | Тесты зелёные, поведение не изменилось |
| 0.2 | Разделение плеера, переходы фаз в `domain/session` | Нет | Сценарии из [SUMMARY.md](SUMMARY.md) проходят как раньше |
| 0.3 | Хранилище v2, миграция v1 → v2, резервная копия и восстановление | Кнопки «Сохранить копию» и «Восстановить» | Миграция на реальной копии данных заказчика без потерь; копия восстанавливается |
| 0.4 | Каталог отдельно от данных: `CatalogExercise`, `maxes` в профиле, тексты по id, разметка паттернов | Нет (данные те же) | Импорт от тренера в старом формате работает; Check-Up пишет в `maxes` |
| 0.5 | Слоты: `WorkoutTemplate`, `resolveWorkout`, старт сессии из разрешённых слотов | Нет | Старые планы ведут себя ровно как раньше |
| 0.6 | Роутер по хэшу, каркас i18n (только инфраструктура и ключи для новых экранов) | Адреса вкладок | Обновление страницы возвращает на ту же вкладку |

Выпуск: после 0.3 — промежуточный релиз (резервная копия полезна сразу), после 0.6 — релиз фундамента, затем шаг 1 (каталог и лестница).

| Профили | У каждого свой телефон | **Один профиль на устройство.** Переключателя профилей нет; модуль Г.1 брифа (мультипрофили) снимается. `StoreV2` хранит один `ProfileData` (поле `profiles` не нужно). Возрастные ограничения остаются |
| Шеринг | Циклом или тренировкой, без подписи автора | `SharePayloadV1.k = 'w' \| 'p'`, поля автора нет |
| Чек-ап | Предложить на первом экране знакомства, не обязателен; значения берутся после первого круга | Стартовые максимумы — `defaultMax` по уровню; калибровка «Как зашёл первый круг?» обновляет `maxes`. Чек-ап — необязательный шаг мастера |
| Импорт и экспорт | Главные элементы, должны быть удобными, «подноготная» не видна | См. раздел 11: JSON и промпты уходят из интерфейса; сценарий «Отправить результаты и создать новую тренировку» |
| Рост каталога | Заказчик с ИИ по шаблону | На шаге 1 — шаблон разметки упражнения и проверка (валидатор) при сборке |

## 11. Импорт и экспорт без «подноготной»

Пользователь не видит JSON, промптов и файлов. Он видит намерения:

- **«Отправить результаты и создать новую тренировку»** → короткие вопросы кнопками («чего хочется») → тренировка или цикл от движка с пояснением → «Начать» / «Сохранить».
- **«Поделиться»** → QR и системное меню «Поделиться» (Web Share API: мессенджеры, соцсети).
- Сохранение и восстановление копии — одна кнопка в настройках, без слова «JSON».

### Кто генерирует: программа (решение заказчика, 24.11.2026)

**Тренировки и циклы составляет движок на телефоне — без ИИ.** Каталог с паттернами, антагонистами и лестницей плюс правила из раздела 1 брифа дают детерминированную генерацию: офлайн, мгновенно, бесплатно, одинаково в России и за её пределами, проверяемо тестами.

| Движок решает | Как |
|---|---|
| Структура | Из цели, времени и частоты: 25 мин — суперсеты антагонистов, 45 мин — 3×6, 60 мин — 4 круга или AGT 15–20 |
| Баланс | Покрытие 8 паттернов за тренировку или неделю, объём по акцентам `Base / + / ++` |
| Порядок | Чередование антагонистов, приоритетная зона в начале круга |
| Квота баланса | Минимум одно одноопорное на низ и одно на верх или кор |
| Условия | Локация, экипировка, `NO TOUCH`, возраст |
| Цифры | Процент от максимума по цели; калибровка после первого круга |
| Прогрессия | По журналу: RIR 2+ на всех кругах → +10% или ступень `+`; провал → ступень `−` |
| «Не скучно» | Ротация внутри паттерна по давности в журнале; «Вариация» = тот же каркас с другим seed |
| Особые режимы | «Спасти неделю», разгрузка, мобильность — шаблоны правил |
| Пояснение | Текст из шаблонов: «Акцент на тягу — противовес сидячей работе» |

Жёсткое правило: жалоба на боль → режим мобильности и совет обратиться к врачу. Ни движок, ни ИИ не подбирают «упражнения от боли».

Качество генерации определяется богатством каталога: нужно около 3–5 упражнений на паттерн в каждой среде по разным ступеням (60–100 упражнений, тексты на трёх языках). **ИИ используется при подготовке каталога** (заказчик с ИИ размечает по шаблону, сборка проверяет разметку), а не во время работы приложения.

### ИИ в приложении: «Обсудить с ИИ» (промежуточное решение)

Встроенного ИИ нет. Приложение готовит **бриф для любого ИИ, который есть у пользователя** (ChatGPT, Gemini, Claude, Алиса, GigaChat, DeepSeek…), и тот отвечает в живом диалоге. Это развитие нынешнего «Конструктора запроса AI» на вкладке Sync / Log.

**Для пользователя:** кнопка «Обсудить с ИИ» → системное меню «Поделиться» (Web Share API) открывает приложение ИИ с готовым текстом; если меню недоступно — «Скопировано, вставьте в свой ИИ». Технических слов в интерфейсе нет.

**Что в брифе** (на языке пользователя, компактно — 2–4 тыс. символов, чтобы влезал в любой чат):
1. Роль и правила: «ты тренер по функциональным тренировкам; задай уточняющие вопросы; при боли — к врачу; не предлагай упражнения вне списка».
2. Профиль: возрастная группа, уровень, цель, время, частота, экипировка, `NO TOUCH`, акценты. Без имени.
3. **Сводка журнала, а не сырые записи:** по паттернам за период с последнего чек-апа — объём, средний RIR, динамика, замены. Это заодно снимает проблему обрезки экспорта до 20 записей.
4. Текущая программа кратко.
5. Список упражнений каталога (id, название, паттерн, ступень) — чтобы ИИ говорил на языке приложения.
6. Инструкция для обратного пути: «если пользователь попросит план, выдай его в конце ответа одним блоком кода по схеме…».

**Обратный путь (необязательный):** кнопка «Вставить план от ИИ» читает буфер обмена, находит в тексте блок по схеме и прогоняет его через движок — проверка упражнений по каталогу, разумность цифр, возрастные ограничения, затем адаптация под условия. Пользователь видит предпросмотр готовой тренировки, а не JSON. Невалидный ответ → понятное сообщение и предложение собрать тренировку движком.

**Почему это хорошо:**
- Бесплатно, без ключей, сервера, лимитов и защиты от злоупотреблений.
- Работает в любой стране: пользователь сам выбирает доступный ему ИИ (в России — Алиса, GigaChat, DeepSeek и др.).
- Живой диалог даёт то, чего не даст движок: разговор о целях, мотивация, объяснение, анализ «как тренер».
- Ответ ИИ всегда проходит через движок, поэтому слабая модель не навредит.

### Встроенный ИИ — позже, если понадобится

Если встроенный ИИ всё же понадобится (одна кнопка без копирования), архитектура готова: прокси с адаптером провайдера (Cloudflare Worker + Claude для международного контура; Yandex Cloud Functions + YandexGPT или GigaChat для российского), ответ по той же схеме и через тот же валидатор движка. Защита: Cloudflare Turnstile, лимит генераций на устройство, лимит трат у провайдера. Оценка: Claude Haiku 5.5 — около $0.0015 за генерацию, Sonnet 5.5 — около $0.03; модель выбирается пробным прогоном на 20 реальных запросах.

### Доступность в России

- Сайт: зеркало на российском хостинге (Yandex Cloud Object Storage, Selectel и т. п.) с отдельным доменом, деплой тем же GitHub Actions; Cloudflare в России работает нестабильно.
- После первой загрузки приложение офлайн и от хостинга не зависит.
- Ссылки шеринга понимают оба домена.
- Claude для пользователей из России не используется: Россия не входит в поддерживаемые Anthropic регионы.

## 12. Лестница через границы паттернов

Сценарий с площадки: 20 кругов AGT 30%, на 15-м круге один тап «−1 ступень» на карточке болгарских выпадов → приседания, тренировка продолжается.

Болгарский выпад — паттерн `lunge`, воздушный присед — `squat`. Лестница «по паттерну» дала бы обратные выпады, а не приседания. Поэтому:

- Лестница строится по **семейству** (`family`, например `legs_knee`: присед, выпады, болгарский), а `pattern` остаётся для учёта баланса паттернов в генераторе.
- У упражнения может быть явный «предпочтительный» сосед `ladder.minus1 / plus1` — он важнее вычисленного. Так заказчик с ИИ задаёт ожидаемые шаги: болгарский −1 = приседания.
- На карточке «15+» и в пошаговом плеере — кнопки **−1 / +1 ступень** прямо на карточке, без окна выбора; `⇄` открывает полный список альтернатив.
- Цель пересчитывается по отношению максимумов (формула брифа). Если максимума для нового упражнения нет — `defaultMax` по уровню, затем калибровка.
- В журнал круги до замены пишутся с болгарским, после — с приседаниями и пометкой `swappedFromName`. Тренер и ИИ видят, на каком круге была замена.

## 13. Личные цели (решение заказчика, 25.11.2026)

Люди ставят конкретные цели к сроку: «3 выхода на две к концу года», «гиперэкстензия 100 кг», «бицепс 80 кг». Цель хранится в профиле и **фоном участвует в формировании тренировок**.

### Модель

```ts
// src/domain/goals/types.ts
export interface Goal {
  id: string;
  exerciseId: string;          // упражнение-цель (каталог или своё)
  kind: 'reps' | 'seconds' | 'weight'; // weight = вес × повторы, сравнение по оценке 1ПМ
  start: { value: number; date: string };   // стартовая точка
  target: number;              // 3 повтора, 120 с, 100 кг
  deadline: string;            // ISO-дата
  status: 'active' | 'done' | 'paused';
}
// ProfileData.goals: Goal[] — 1–3 активные; в QR и бриф получателю не уходят
```

### Как цель работает в движке

1. **Приоритет:** паттерн и семейство упражнения-цели получают акцент `++` — оно в начале круга, с развивающим объёмом; остальное в поддерживающем режиме.
2. **Путь по лестнице:** для навыков цель — вершина семейства (подтягивания → до груди → взрывные → выход с резинкой → негативный выход → выход). Генератор выбирает текущую ступень на пути и переводит выше, когда она закрыта с запасом (RIR 2+ на всех кругах).
3. **Темп:** по старту, текущему уровню и сроку — нужный прирост в неделю; цели слотов растут по графику, разгрузка раз в 4–5 недель.
4. **Контрольные точки:** раз в 2–4 недели в тренировку встраивается короткий тест упражнения-цели (или ступени на пути).
5. **Прогресс и прогноз:** карточка на главном экране — «сейчас / цель / срок», график, «идёте по графику» или «отстаёте на N недель».
6. **Проверка реализма:** если нужный темп выше безопасного (граница по типу упражнения и возрастной группе), приложение говорит об этом и предлагает промежуточную цель или другой срок.
7. **ИИ:** цели входят в бриф «Обсудить с ИИ».

Модуль `src/domain/goals/`: путь по лестнице к цели, оценка текущего уровня по журналу, нужный темп и прогноз, проверка реализма, веса приоритетов для генератора — чистые функции с тестами.

### Зависимости

- **Навыки на собственном весе** (выходы, «пистолет», стойка) — на нынешней модели: нужны упражнения пути в каталоге (шаг 1).
- **Цели с весом** требуют того же, что «Зал»: вес в подходе (`SetLog.weightKg`), цель слота «кг × повторы», оценка 1ПМ по подходам (например, формула Эпли: 60 кг × 8 ≈ 76 кг). Цели с весом и «Зал» проектируются в одном документе.
- **Изолирующие упражнения** (бицепс, трицепс, икры) не входят в 8 базовых паттернов: для зала нужна категория «изоляция», которую генератор добавляет поверх базовых паттернов, а не вместо них.

### Где в плане

- Модель цели, вопрос «есть ли цель к сроку» в мастере старта и карточка прогресса — шаг 2.
- Учёт цели в генераторе (приоритет, путь, темп, контрольные точки) — правила генератора шагов 1–2.
- Цели с весом — вместе с «Залом».

## 14. Ступени здоровья и «Форма и энергия» (решение заказчика, 25.11.2026)

Экран «Цель» мастера старта — [SPEC_WIZARD_GOAL_SCREEN.md](SPEC_WIZARD_GOAL_SCREEN.md).

### Ступени вместо взаимоисключающих целей

Цель всегда здоровье; ступень задаёт состав нагрузки, и каждая следующая включает предыдущие:

```ts
export type HealthLevel = 'mobility' | 'form' | 'strength'; // ProfileData.healthLevel
// доли компонентов в неделе — ориентир для генератора
const LEVEL_MIX: Record<HealthLevel, { mobility: number; form: number; strength: number }> = {
  mobility: { mobility: 1.0, form: 0, strength: 0 },
  form: { mobility: 0.2, form: 0.8, strength: 0 },
  strength: { mobility: 0.15, form: 0.3, strength: 0.55 },
};
```

Прежние «физиологические режимы» брифа (раздел 1.2) становятся компонентами: «Анти-стул / Mobility» — мобильность; «AGT 30%» и «Поддержание» — форма и энергия; «Сила 80%» — сила. Генератор раскладывает неделю по долям ступени с учётом времени и частоты; светофор самочувствия поправляет конкретный день.

### «Форма и энергия»: вход и результат

Вес — плохой показатель (растут мышцы, меняется вода), калории тренировок нельзя измерить точно и они — только половина баланса. Поэтому разделяем **управляемый вход** и **результат**:

| | Метрика | Хранение | Отображение |
|---|---|---|---|
| Вход | Активные минуты и MET-часы за неделю: тренировки (тип × длительность), кардио из журнала, позже — шаги | вычисляется из журнала | недельная цель «≥ N ч движения»; калории — **диапазоном** как оценка (MET × вес × время, ±25%) |
| Результат | **Обхват талии** (главный; ориентир — талия < ½ роста), вес по желанию | `ProfileData.bodyMetrics: { date, waistCm?, weightKg? }[]` | график раз в 1–2 недели; вес — скользящее среднее за 7 дней |

Цель к сроку может быть типа «талия» или «вес тела» (расширение модели `Goal` из раздела 13: `kind: 'waist' | 'bodyweight'`), с проверкой безопасного темпа (для веса — 0,5–1% в неделю).

### Принципы

- В интерфейсе нет «похудения» и «сжечь N ккал»: человек видит часы движения и сантиметры.
- Одна честная строка в цели: результат по форме больше зависит от питания, чем от тренировок; вопросы о питании — через бриф «Обсудить с ИИ». Подсчёта калорий еды в приложении нет.
- `bodyMetrics` и цели — только на устройстве, вне QR; в бриф — по согласию.
- Модуль `src/domain/activity/`: MET-таблица по типам тренировок и кардио, недельная сумма, оценка калорий диапазоном, тренд талии и веса — чистые функции с тестами.

### Где в плане

- Ступень, личная цель, талия и вес на экране «Цель», недельная цель активности и карточка прогресса — шаг 2 (мастер старта).
- Доли ступеней и режим «форма» в генераторе — правила генератора шагов 1–2.
- Шаги из часов или телефона — позже, по необходимости.
