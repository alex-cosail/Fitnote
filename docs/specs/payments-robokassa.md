# Техническое задание: Подсистема приема платежей и управления платным доступом

## 1. Цель и бизнес-контекст
Реализовать в приложении функционал разовой оплаты доступа к расширенным возможностям (стоимость — 300 ₽). 

**Ключевое архитектурное требование:** На этапе запуска (MVP) прием платежей осуществляется через агрегатор **Robokassa** (статус исполнителя — самозанятый / НПД). Архитектура должна обеспечивать возможность дальнейшего переключения на интернет-эквайринг **Т-Касса (Т-Банк)** при смене налогового статуса на ИП **без обновления клиентского приложения** и без потери истории транзакций.

---

## 2. Роли и границы ответственности компонентов

### 2.1. Клиентское приложение (Frontend / Mobile / Web)
* Отвечает исключительно за отображение статуса подписки/доступа, инициацию запроса на оплату и открытие платежной ссылки.
* **Запрещено:** хранить в клиентском коде секретные ключи, логику генерации подписей, прямые URL платежных шлюзов или нативные SDK конкретных провайдеров.
* Взаимодействует только с собственным Backend API.

### 2.2. Серверная часть (Backend / Payment Gateway Adapter)
* Реализует паттерн **«Адаптер» (Strategy / Provider Interface)** для работы с платежными шлюзами.
* Управляет жизненным циклом заказов (`orders`) и статусом платного доступа пользователя (`is_pro`).
* Обеспечивает фискализацию (передачу номенклатуры для формирования чеков по 54-ФЗ / НПД).
* Принимает и валидирует входящие серверные уведомления (Webhooks) от платежных систем.

---

## 3. Функциональные требования

### 3.1. Сценарий оплаты (User Flow)
1. Пользователь нажимает кнопку «Оплатить 300 ₽» в интерфейсе приложения.
2. Клиент отправляет авторизованный запрос `POST /api/v1/payments/create` на бэкенд (передавая идентификатор продукта/тарифа).
3. Бэкенд создает запись о заказе в БД со статусом `pending`, присваивает внутренний уникальный `order_id` (числовой или UUID, совместимый с требованиями обоих шлюзов — для Robokassa требуется уникальный числовой `InvId`).
4. Бэкенд обращается к активному провайдеру (на старте — Robokassa), формирует ссылку на оплату (`payment_url`) и возвращает её клиенту.
5. Клиент открывает `payment_url` во внешнем браузере или in-app браузере (Custom Tabs / SFSafariViewController).
6. После успешной оплаты пользователь возвращается в приложение (по Deep Link / Universal Link или закрытию вкладки), а клиент запрашивает обновленный статус профиля (`GET /api/v1/user/status`).

### 3.2. Обработка уведомлений об оплате (Webhooks)
1. Бэкенд предоставляет изолированные эндпоинты для приема уведомлений от каждого провайдера:
   * `POST /api/v1/webhooks/robokassa` (ResultURL)
   * `POST /api/v1/webhooks/tbank` (NotificationURL — закладывается в архитектуру на будущее)
2. При получении вебхука бэкенд обязан:
   * Проверить цифровую подпись запроса (MD5/SHA-256 для Robokassa; SHA-256 токен для Т-Банка) с использованием секретных ключей из переменных окружения.
   * Проверить идемпотентность: если заказ `order_id` уже имеет статус `paid`, вернуть успешный ответ шлюзу без повторного начисления прав.
   * Сверить сумму платежа с суммой заказа в БД (300.00 RUB).
   * В рамках одной транзакции БД перевести заказ в статус `paid` и активировать платный доступ пользователю (`is_pro = true`).
   * Вернуть корректный HTTP-ответ платежному шлюзу (`OK{InvId}` для Robokassa, `200 OK` с телом `OK` для Т-Банка).

### 3.3. Переключение провайдеров (Hot-Swap)
* Выбор активного провайдера для новых платежей регулируется конфигурационной переменной на сервере (`ACTIVE_PAYMENT_PROVIDER = robokassa | tbank`).
* В переходный период допускается одновременная обработка вебхуков от обоих шлюзов (для завершения транзакций, начатых до момента переключения).

## 4. Требования к модели данных (Минимальная схема БД)

Архитектору необходимо предусмотреть как минимум две логические сущности:

### Таблица `orders` (Заказы)
* `id` (BIGSERIAL / INT, Primary Key) — внутренний числовой номер заказа (используется как `InvId` в Robokassa и как `OrderId` в Т-Банке).
* `user_id` (UUID / INT, Foreign Key) — идентификатор пользователя.
* `provider` (VARCHAR) — имя провайдера (`robokassa`, `tbank`).
* `external_payment_id` (VARCHAR, nullable) — ID транзакции на стороне платежного шлюза.
* `amount` (DECIMAL(10, 2)) — сумма заказа (`300.00`).
* `status` (ENUM: `pending`, `paid`, `failed`, `canceled`) — статус заказа.
* `created_at` / `paid_at` (TIMESTAMP) — метки времени создания и оплаты.

### Поля в таблице `users` (Пользователи)
* `is_pro` (BOOLEAN, default `false`) — флаг наличия платного доступа.
* `pro_activated_at` (TIMESTAMP, nullable) — дата и время активации.

## 5. Спецификация API (Контракт между клиентом и сервером)

### 5.1. Создание платежа
* **Endpoint:** `POST /api/v1/payments/create`
* **Headers:** `Authorization: Bearer <token>`
* **Request Body:**
  ```json
  {
    "product_id": "pro_access_lifetime"
  }
  ```
* **Response (200 OK):**
  ```json
  {
    "order_id": 1042,
    "payment_url": "https://auth.robokassa.ru/Merchant/Index.aspx?..."
  }
  ```

### 5.2. Проверка статуса доступа
* **Endpoint:** `GET /api/v1/user/access`
* **Headers:** `Authorization: Bearer <token>`
* **Response (200 OK):**
  ```json
  {
    "is_pro": true,
    "activated_at": "2026-11-27T10:30:00Z"
  }
  ```

## 6. Требования безопасности и юридические аспекты
1. **Защита секретов:** Все пароли и ключи (`MerchantLogin`, `Password#1`, `Password#2` для Robokassa; `TerminalKey`, `Password` для Т-Банка) хранятся строго в защищенном хранилище секретов / переменных окружения сервера.
2. **Юридические реквизиты и оферта:** Тексты пользовательского соглашения, оферты и реквизиты продавца (ФИО и ИНН самозанятого на этапе 1; наименование и ОГРНИП ИП на этапе 2) должны отдаваться с бэкенда или открываться по веб-ссылке, чтобы исключить необходимость релиза новой версии приложения при смене статуса.
3. **Фискализация (чеки):** При формировании платежа в Robokassa передавать объект номенклатуры (`Receipt`) согласно требованиям сервиса «Робочеки» для автоматической отправки чека покупателю и регистрации дохода в ФНС («Мой налог»).

## 7. Критерии приемки (Definition of Done)
1. Проведена успешная тестовая оплата в песочнице (Test Mode) Robokassa с корректной отработкой вебхука и изменением флага `is_pro` в БД.
2. Проверена защита вебхука: запрос с неверной контрольной суммой отклоняется со статусом `403 Forbidden` и не меняет статус заказа.
3. Проверена идемпотентность: повторная отправка валидного вебхука по уже оплаченному заказу не вызывает ошибок и дублей в БД.
4. Клиентское приложение корректно разблокирует платный функционал после возврата со страницы оплаты без перезапуска приложения.
